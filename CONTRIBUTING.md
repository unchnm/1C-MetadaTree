# Правила разработки 1C-MetadataTree

Этот файл описывает правила сопровождения форка CDT 41 и его обновления из родительского репозитория.
Общие команды сборки и тестов описаны в [DEVELOPING.md](DEVELOPING.md).

## Репозитории и ветки

- `origin` — репозиторий `unchnm/1C-MetadataTree`, куда отправляются наши изменения.
- `upstream` — оригинальный репозиторий `lekot/VScodePluginFor1CDev`, откуда получаются обновления CDT 41.
- `main` — проверенная основная версия проекта.
- `feature/<name>` — новая функциональность.
- `fix/<name>` — исправление ошибки.
- `sync/upstream-<date>` — отдельная ветка для слияния обновлений оригинала.
- `experiment/<name>` — прототипы, которые ещё не должны попадать в основную версию.

Не выполнять `git push --force` в `main` или в рабочую ветку. Не переписывать историю опубликованных веток без отдельного решения.

Перед началом работы проверить состояние:

```bash
git status --short --branch
git branch -avv
git remote -v
```

Если `upstream` ещё не настроен:

```bash
git remote add upstream https://github.com/lekot/VScodePluginFor1CDev.git
git fetch upstream
```

## Разработка новой функции

1. Обновить локальный `main` из `origin`.
2. Создать отдельную ветку `feature/` или `fix/`.
3. Изучить существующую реализацию и тесты до изменения кода.
4. По возможности добавить новые файлы для нашей логики вместо изменения больших файлов оригинала.
5. Изменить оригинальный файл только в необходимой точке подключения.
6. Добавить тест, который проверяет пользовательское поведение.
7. Запустить сборку и относящиеся к изменению тесты.
8. Сделать отдельный тематический коммит.
9. Проверить diff и только после этого отправить ветку в `origin`.

Один коммит должен описывать одну связанную доработку. Не смешивать в одном коммите исправление поиска, изменения конструктора запросов, форматирование файлов и случайные исправления тестов.

Если одну функцию приходится менять в нескольких файлах, это всё равно один тематический коммит. Независимые функции оформлять отдельными коммитами — так их проще переносить, откатывать и разбирать при конфликте с `upstream`.

## Обновление из оригинального репозитория

Обновление выполнять в отдельной ветке:

```bash
git switch main
git pull --ff-only origin main
git fetch upstream
git switch -c sync/upstream-YYYY-MM-DD
git merge --no-ff upstream/main
```

После слияния:

```bash
git diff --check
npm run compile
npm run test:ci
npm run package
```

Затем проверить пользовательские сценарии в VS Code, создать pull request из `sync/` в `main` и только после проверки объединить его.

При конфликте в общем файле не выбирать целиком только нашу или только оригинальную версию. Сначала сохранить обе необходимые функции, затем проверить команды, `package.json`, контекстные меню, идентификатор расширения и тесты.

История текущей ветки была получена из сокращённой копии Git. В полной рабочей копии перед первым слиянием убедиться, что история не shallow:

```bash
git rev-parse --is-shallow-repository
```

Если результат `true`, получить полную историю до слияния:

```bash
git fetch --unshallow origin
```

## Правила для изменений форка

Наши изменения должны оставаться узнаваемыми и отделимыми от кода оригинала.

- Собственные сервисы, провайдеры, команды и тесты размещать в отдельных файлах.
- Для регистрации функции в оригинальном коде делать короткую точку подключения.
- В общих исходных файлах помечать наши блоки парными комментариями `1C-MetadataTree`:
  - TypeScript/JavaScript: `// 1C-MetadataTree: begin ...` и `// 1C-MetadataTree: end ...`;
  - CSS: `/* 1C-MetadataTree: begin ... */` и `/* 1C-MetadataTree: end ... */`;
  - HTML/Webview: `<!-- 1C-MetadataTree: begin ... -->` и `<!-- 1C-MetadataTree: end ... -->`.
- Ставить маркеры в начале и конце собственного блока, а не на каждой строке. Маркеры должны кратко объяснять назначение блока и помогать найти его при слиянии с `upstream`.
- В JSON комментарии невозможны: такие изменения фиксировать в `CONTRIBUTING.md` и отдельном тематическом коммите.
- В собственных новых исходных файлах добавлять заголовок `1C-MetadataTree` с кратким назначением файла.
- Не переписывать большой файл оригинала ради косметического изменения.
- Не смешивать изменение окончаний строк с логикой.
- Не удалять существующее поведение оригинала без отдельного описания причины.
- Сохранять `publisher: unchnm`, имя расширения `1c-metadata-tree` и идентификатор `unchnm.1c-metadata-tree`.
- При добавлении команды проверить команду в `contributes.commands`, регистрацию обработчика и контекстное меню отдельно.
- При изменении Webview проверять собранный Webview и запускать сценарий в реальном VS Code.
- При переносе кода из другого проекта сохранять его лицензию и указывать источник.

## Правила для нейросети или другого автоматического помощника

Перед изменением репозитория помощник обязан:

1. Прочитать этот файл и `DEVELOPING.md`.
2. Проверить ветку, удалённые репозитории и незакоммиченные изменения.
3. Не удалять и не переписывать чужие незакоммиченные файлы.
4. Найти существующую команду, сервис, тест и точку регистрации, относящиеся к задаче.
5. Сначала предложить или создать изолированную ветку, если работа не является мелким исправлением текущей ветки.

Во время работы помощник должен:

- делать изменения небольшими тематическими шагами;
- отделять код форка от изменений оригинала;
- не добавлять Java, внешние рантаймы или новые зависимости без явного обоснования;
- не заменять рабочую реализацию экспериментом без сохранения отката;
- не объявлять работу проверенной без запуска соответствующей проверки;
- сообщать, если проверка выполнена только на синтетической конфигурации;
- не менять версию расширения без необходимости;
- не коммитить `node_modules`, временные файлы и журналы;
- не выполнять принудительную отправку в Git;
- не удалять ветки, релизы или историю без отдельного подтверждения.

В финальном сообщении помощник указывает:

- что изменено;
- какие файлы и команды затронуты;
- какие тесты и сборки прошли;
- что не проверялось на реальном Windows/VS Code;
- commit, ветку и ссылку на VSIX, если VSIX был собран.

## Сборка и VSIX

Исходный проект содержит сборщик VSIX:

```bash
npm run compile
npm run package
```

Готовые VSIX предпочтительно публиковать в GitHub Releases, а не хранить в Git. Если в репозитории временно оставляется один последний VSIX для ручной установки, старые версии удаляются из Git, а файл текущей версии явно указывается в описании изменения.

## Как искать наши участки при конфликте

```bash
rg -n "1C-MetadataTree" src test
git diff upstream/main...HEAD
```

Сначала разрешать конфликты в отмеченных блоках, затем отдельно проверять соседний код оригинала. После разрешения конфликта маркер должен остаться у сохранённой форк-доработки. Если блок был заменён новой реализацией, обновить карту коммитов и удалить устаревший маркер.
